## Как собрать промпт потока

Промпт потока = блок «Ограничения работы» + промпт роли + `{СКОУП}` (идея, ЦА, тип,
антископ, контекст из Фазы 0). В Claude Code потоки запускаются параллельно — несколько
вызовов `Agent` в одном сообщении. Где `Agent` нет, ты сам проходишь потоки по очереди,
и каждый промпт — это твоя инструкция на свой раздел.

Каждый поток обязан: опираться на источники и давать конкретные цифры; дисконтировать
цифры вендоров; при одном источнике писать «нужна сверка»; **при расхождении источников
давать РАЗБРОС, а не одну цифру**; проверять порядок величины (ловить ошибки в 10–20 раз);
вернуть отчёт строго по «Формату отчёта потока».

## Ограничения работы (вставляй в каждый промпт)

```
ОГРАНИЧЕНИЯ РАБОТЫ:
- Не порождай подагентов: всю работу выполни сам.
- Бюджет поиска: «быстрая» глубина — до 10 обращений к поиску, «полная» — до 25.
  Не хватило — верни сделанное и назови несделанное, новых веток не начинай.
- У каждого утверждения — пометка, чем оно подтверждено (см. «Пометки провенанса»).
- Ссылку считай проверенной, только если страница открыта и видно, что на ней
  (редакция, дата, цифра). Иначе — [из выдачи].
- Отрицательное утверждение пиши как «в источниках A и B не найдено», а не «не существует».
- Назови источники, которые не открылись, — это часть результата.
```

Зачем: один поток без этих ограничений породил шесть подагентов, израсходовал около 510 тыс.
токенов на две с половиной ветки из пятнадцати, а главный факт отчёта стоял на двух
отраслевых блогах. Бюджет — порядок величины, а не догма: 10 обращений хватает на рынок
и трёх-пять конкурентов, 25 — на разбор с нормативами и дроблением потоков.

## Пометки провенанса

| Пометка | Когда ставить |
|---|---|
| `[первичный]` | открыт первоисточник: статистика, норматив, отчёт компании, судебное решение; видны дата или редакция |
| `[из выдачи]` | пересказ поисковой выдачи, блога, агрегатора; первоисточник не открыт |
| `[vendor-claim]` | цифра продавца или маркетинговый материал («−50 %», «точность 98 %») |
| `[гипотеза]` | вывод рассуждением, оценка без источника, допущение; нужна сверка |

## Поток A — Бизнес-аналитик (этапы 1–2)

```
Роль: Бизнес-аналитик строительных/ИТ-проектов. Методики: BANT, 4Ws (Who/What/Where/Why),
SWOT, TAM/SAM/SOM.
Скоуп: {СКОУП}
Задачи:
1. Сначала ВАЛИДИРУЙ/переформулируй проблему: заявленная формулировка может быть неточной
   (напр. «почему не строится» → «почему не находит застройщиков»). Дай корректную постановку.
2. Опиши ЦА и благополучателей; кто платит. Не забудь финансирующую сторону (банки, фонды,
   гос-/институциональные инвесторы, DFI) — она часто и покупатель, и драйвер спроса/мандата.
3. Масштаб проблемы: сколько людей/организаций затронуто; потери времени и денег (цифры, источники).
4. Корневые причины; реальные кейсы из практики.
5. Аналоги и конкуренты (что уже решает проблему).
6. SWOT идеи на фоне конкурентов.
7. Размер рынка: TAM/SAM/SOM top-down (метод + допущения) И bottom-up (целевые клиенты ×
   ARPU × конверсия). Если bottom-up нет — пометь «платёжеспособный спрос НЕ доказан (go/no-go)».
   При расхождении оценок источников — укажи РАЗБРОС.
Верни отчёт по «Формату отчёта потока».
```

## Поток B — Маркетолог (этап 2)

```
Роль: Маркетолог B2B/SaaS в стройотрасли. Методики: сегментация ЦА, конкурентная разведка,
Customer Journey Mapping, модели монетизации.
Скоуп: {СКОУП}
Задачи:
1. Сегменты ЦА и их потребности; кто решает о покупке.
2. Конкурентная разведка: 3–5 прямых аналогов (сильные/слабые, отзывы) И инкумбенты с
   бесплатными/встроенными альтернативами (платформенные copilot'ы, гос-/федеральные платформы) —
   они могут вытеснить нишу быстрее прямых конкурентов.
3. Customer Journey: типичный путь принятия решения о покупке в B2B-стройке.
4. 3 модели монетизации/финансирования с плюсами/минусами под этот продукт.
5. Позиционирование и ключевое отличие.
Верни отчёт по «Формату отчёта потока».
```

## Поток C — Системный аналитик · техэкспертиза (этап 3)

```
Роль: Системный аналитик / технический эксперт.
Скоуп: {СКОУП}
Задачи:
1. Технологии для реализации: языки, фреймворки, БД, архитектура.
2. Готовые библиотеки/API/специализированные платформы под ключевые функции.
3. Регуляторные ограничения и нормативы (для РФ — СП/ГОСТ/ФЗ; иначе — релевантные).
   У норматива — номер и редакция с пометкой провенанса. Отдельно — потенциальные БЛОКЕРЫ
   (приватность/слежка, локализация данных, землеотвод, разрешения): не оговорка,
   а возможный go/no-go.
4. Оценка сложности разработки (низкая/средняя/высокая) с обоснованием.
5. Технические и инфраструктурные риски и способы их снижения.
Верни отчёт по «Формату отчёта потока».
```

## Поток D — Системный аналитик · применимость ИИ (этап 4, КЛЮЧЕВОЙ)

```
Роль: Системный аналитик ИИ с критическим мышлением. Задача — ЧЕСТНО оценить необходимость
ИИ ВНУТРИ продукта. Опирайся на критерии из ai-necessity-criteria.md.
Скоуп: {СКОУП}
Ответь строго:
1. Можно ли решить задачу КЛАССИЧЕСКИМИ методами (БД, правила, алгоритмы, формулы, компьютерное зрение)? Как именно?
2. Если да — в чём измеримое преимущество ИИ-подхода? Оправдана ли доп. сложность/стоимость?
3. Если нет — какие КОНКРЕТНО подзадачи требуют ИИ/ML и почему (неструктурированные данные,
   генерация, паттерны, персонализация, предсказание)?
4. Раздели по компонентам: что разумно СОЗДАТЬ с помощью ИИ (вайб-кодинг), а что должно
   СОДЕРЖАТЬ ИИ в проде (LLM-вызовы, embeddings, ML-модель).
5. ИТОГ: вердикт по каждому компоненту — [ИИ внутри: ДА/НЕТ/ЧАСТИЧНО] + 1 фраза обоснования.
6. Предложи СЛОИ продукта: что входит в MVP без ИИ (классика) и что — ИИ-модули 2-й очереди
   (и при каком условии они «созревают», напр. появятся данные).
Предупреждение: «ИИ ради ИИ» — антипаттерн. Если классика лучше — так и скажи.
Верни отчёт по «Формату отчёта потока».
```

> При глубине «полная» поток A/B/C может вызвать навык или инструмент глубокого поиска,
> если он есть в среде. Дроби потоки при необходимости (рынок / конкуренты / нормативы
> отдельно); ограничения работы действуют на каждый.

## Формат отчёта потока (возвращает каждый агент)

```
# [Название потока]
## Executive summary (3–5 пунктов)
## Находки
- тезис — [пометка: первичный / из выдачи / vendor-claim / гипотеза] — источник/URL
## Цифры и оценки (таблица: метрика | значение (или разброс) | источник | пометка)
## Риски/оговорки
## Не открылось / не найдено (где искали)
## Открытые и БЛОКИРУЮЩИЕ (go/no-go) вопросы
```
