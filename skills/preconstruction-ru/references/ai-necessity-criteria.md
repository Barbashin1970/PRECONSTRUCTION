# Критерии: нужен ли ИИ ВНУТРИ продукта (этап 4)

Опора потока D и аудита вердикта по ИИ. Цель — **честно** ответить, нужен ли ИИ
в работающем продукте, а не «как покрасивее вставить ИИ». Не все проекты должны
содержать ИИ: многие хорошие ИТ-решения для стройки **созданы С ПОМОЩЬЮ** ИИ,
а работают на классических технологиях.

## «С помощью ИИ» и «ИИ внутри»

| | Создано **С ПОМОЩЬЮ** ИИ | Содержит ИИ **ВНУТРИ** |
|---|---|---|
| Что это | код написан с ChatGPT, Copilot, Cursor (вайб-кодинг) | в продакшене работают ML-модели, вызовы LLM, поиск по embeddings |
| Финальный продукт | классическое приложение | ИИ — часть рантайма |
| Пример | калькулятор смет, написанный с ИИ, но считающий по формулам | поиск по регламентам через embeddings |

Путать эти две вещи — корневая ошибка. В питче за неё отвечает обязательный раздел
«Применимость ИИ».

## Когда ИИ внутри действительно нужен

- неструктурированные данные: тексты, изображения, видео;
- обучение на больших данных;
- распознавание паттернов, которые трудно записать правилами;
- генерация: контент, планировки;
- персонализация по поведению пользователей;
- предсказательная аналитика.

## Когда хватает классических методов

- чёткие правила и логика;
- детерминированные вычисления, калькуляторы по формулам;
- CRUD-операции с базой данных;
- фильтрация, сортировка, агрегация структурированных данных.

## Протокол честной оценки

1. Можно ли решить задачу **классическими** методами (БД, правила, алгоритмы)?
2. Если да — в чём измеримое преимущество ИИ? Оправдана ли дополнительная сложность и цена?
3. Если нет — какие **конкретно** подзадачи требуют ИИ/ML?
4. Что **создать** с помощью ИИ, а что должно **содержать** ИИ в финале?
5. Вердикт по компонентам: ДА / НЕТ / ЧАСТИЧНО, и слои — MVP без ИИ → ИИ 2-й очереди
   с условием, при котором слой «созревает» (появились данные, разметка, бюджет).

## Примеры вердиктов

| Задача | Вердикт |
|---|---|
| разбор документов в базу | С ПОМОЩЬЮ ИИ один раз, дальше обычная БД |
| поиск по регламентам по смыслу | ДА: поиск по embeddings |
| калькулятор стоимости по параметрам | НЕТ: формул и правил достаточно |
| генерация планировок | ДА: генеративная модель |
| размеры с чертежей | НЕТ для LLM: специализированное компьютерное зрение |

## Пределы LLM: кейс с чертежами фасадов

Строительная компания хотела по PDF-чертежам фасадов получать ведомость объёмов. LLM
«выдумывала» размеры: числа сливались (`670` и `450` → `670450`), часть терялась, площадь
фасада посчитать было нельзя. Причина — LLM работает с токенами, а не с геометрией
изображения, и не делает пространственного анализа.

| LLM подходит | LLM не подходит |
|---|---|
| обзоры, сравнительные таблицы, оценка зрелости решений | точное распознавание размеров на чертежах |
| исследование инструментов, отзывов, market research | пространственный анализ геометрии |
| расчёт окупаемости подписок, сценарии | прямая автоматизация сложной техработы |

Правильный ход: LLM проводит исследование и сравнивает специализированные платформы
(KREO, Togal.AI, Bluebeam Revu — пометка `[vendor-claim]` для их цифр точности),
а внедряют их **после теста на реальных чертежах** — или отказываются, если невыгодно.

> Честность этой оценки ценится выше «крутости ИИ». Признать, что классика лучше, —
> сильный ход, а не слабый.
